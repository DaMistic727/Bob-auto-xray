# План безопасного E2E Bob Doctor на одноразовой Ubuntu VPS

Этот план выполняется только на явно выделенной одноразовой VPS с разрешённым reboot и тестовыми данными. Production и чужой сервер не подходят. Doctor не использует эти шаги автоматически. Все снимки и временные скрипты E2E создаются вне `/var/lib/selfsni` с правами `0700/0600`; в отчёт попадают только хэши, счётчики и обезличенные результаты.

## Подготовка и матрица

1. Зафиксировать commit кандидата, SHA256 release archive и bootstrap; установить именно проверенный архив. Проверить заполненные `menu_commit` и `menu_archive_sha256` в `versions.lock.json`; опубликованный v0.3.4 не менять.
2. Подготовить отдельные чистые одноразовые Ubuntu VPS: (A) 26.04.1 amd64 с новым WARP `install`; (B) `--no-warp`; (C) `--adopt-warp` с заранее работающим WARP. Python 3.10/3.12 проверить в CI; при доступности отдельных Ubuntu 22.04/24.04 выполнить их runtime E2E. Записать ОС, архитектуру и версии, без публикации адресов.
3. На каждой завершённой установке добавить через панель **постоянного тестового клиента** в основной REALITY inbound и отдельный дополнительный inbound. Проверить внешним клиентом VLESS/Vision до Doctor и после него. Сохранить тестовые credentials в закрытом хранилище, не в отчёте.

## Снимок до Doctor

На каждой VPS сохранить в закрытом временном каталоге: SHA256, размер и mtime `state.json`; значения `installation_id`, `status`, `stage`, `resume_count`; наличие и метаданные installer lock; хэши runtime Xray JSON, Certbot renewal/deploy hook, TLS key/cert, GeoData, `/etc/fstab`, IPv6/BBR sysctl и управляемых unit/networkd drop-in; логический хэш inbound/client/routing из read-only снимка 3x-ui без вывода UUID или ключей; количество клиентов и inbound; `systemctl` состояние, PID и счётчики рестартов служб; режим WARP, хэш его регистрационных файлов и настроек; UFW/Fail2ban, интерфейсы, IPv6-адреса и список listeners; размер, права и активность SWAP. Для SQLite учитывать WAL и сравнивать **логические строки**, а не только байтовый хэш DB. Сохранить доказательство успешного внешнего тестового клиента.

## Прогоны

1. Выполнить `bob doctor --json` и `bob doctor --deep --json` от root. Проверить один валидный JSON-объект, стабильные ID/порядок, exit code и отсутствие FQDN, email, URL панели/подписки, token, пароля, private key, UUID и Short ID в stdout/stderr. Выполнить обычный текстовый вывод и `--help`.
2. В режиме B ожидать `SKIP` у WARP, отсутствие WARP outbound/rule в Xray и отсутствие вызовов `warp-cli`/WARP trace. В A/C ожидать install/adopt в state, ровно один `warp-outbound` на loopback SOCKS5, активный `warp-svc`, правильные JSON status/settings и функциональный SOCKS trace только в deep. На A проверить активные BBR/FQ, все IPv6-интерфейсы и persistent networkd/sysctl; созданный SWAP — по `/swapfile`, `/etc/fstab` и `swapon`. Для старой ноды без управляемого SWAP ожидать `SKIP`, для штатно пропущенного SWAP — `SKIP`.
3. Во время обоих запусков поддерживать активную сессию независимого VLESS/Vision-клиента и передачу трафика; если внешней клиентской машины нет, отметить **NOT TESTED**. Повторить снимок. `state.json`, stage/status/resume_count, config, логические строки клиентов/inbound/routing, сертификаты, GeoData, UFW, sysctl, networkd, `/etc/fstab`, регистрация WARP и SWAP должны остаться неизменными. Doctor не должен создать installer lock, перезапустить службы или отключить постоянного клиента. Учитывать допустимые побочные эффекты probes: записи обычных service/access logs, счётчики соединений и PHP-сессия после deep GET; не считать их изменением конфигурации.
4. Перезагрузить **одноразовую** VPS, дождаться служб и внешнего подключения постоянного клиента. Повторить default/deep и снимок. PID и время запуска после reboot закономерно меняются; проверять сохранность логического состояния и отсутствие дополнительных рестартов от Doctor.
5. На отдельной VPS со старым релизом проверить путь разового запуска Doctor из проверенного архива. Отсутствие новой глобальной команды ожидаемо; старый или неподтверждённый state должен дать UNKNOWN без изменения прежней установки.

## Безопасная имитация отказов

Ничего не останавливать и не редактировать в рабочей конфигурации. В отдельном Python-процессе на одноразовой VPS запускать `Doctor` с узким `Probe`-адаптером, который подменяет **только ответ одной проверки**, оставляя остальные реальные read-only probes: inactive Xray, отсутствующий Unix socket, истёкший/близкий к истечению сертификат, inactive certbot.timer, WARP disconnected, чужой SOCKS5 PID, потерянный ответ команды, timeout HTTPS GET и Cloudflare trace, отключённый IPv6-интерфейс, повреждённый SWAP и persistent-файл. Для неполного state направить только Doctor на отдельный временный JSON через локальный override константы `STATE`. Проверить PASS/WARN/FAIL/SKIP/UNKNOWN и коды 0/1/2/3. Удалить временные тестовые файлы после сравнения; не использовать `systemctl stop`, Certbot renew, изменение клиентов, UFW, WARP, sysctl или SWAP для инъекции отказа.

## Критерий завершения

Default и deep не меняют указанные конфигурации или установочное состояние, клиент остаётся подключаемым, отчёты не раскрывают секреты, а все неподтверждённые проверки дают UNKNOWN вместо ложного HEALTHY. Любое различие сначала объяснить через реальные журналы/метрики, затем повторить на свежей одноразовой VPS. Результаты A, B, C, активного клиента и reboot отмечать раздельно. До этого E2E Doctor считается готовым только к ревью и испытанию на одноразовой VPS, не к заявлению о подтверждённой production-безопасности.
